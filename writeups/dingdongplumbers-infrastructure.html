Ding Dong Plumbers: Six Years of Production Web Infrastructure

What started as "can you help with the website" in 2019 became an ongoing IT engagement covering domain management, DNS, edge security, CI/CD, and SEO automation. Here is how the stack is built and the reasoning behind every layer.

Production Cloudflare DNS CI/CD Static Site Security Hardening SEO

The Engagement

Ding Dong Plumbers is a Gauteng plumbing business, PIRB registered, in operation since 2008. I started doing IT work for them in 2019, originally just to fix a broken website. Six years later I am still the sole technical contact for everything that lives behind the dingdongplumbers.co.za domain.

This is unpaid, treated as a long-running personal project and a real-world testbed for the skills my certifications cover. Everything is documented and the owner has given me permission to publish what is here.

Why Static

The first version of the site in 2019 was a WordPress install on shared hosting. It worked, but it became a maintenance and security headache fast. Plugin updates, login brute force attempts in the access logs, database backups, theme conflicts, occasional defacements. For a small plumbing business that did not need a blog or a logged-in user area, none of that complexity earned its keep.

I migrated to a static architecture. The reasoning is straightforward when you frame it against the CIA triad:

  • Confidentiality: No database, no user accounts, no admin login panel. There is nothing private to leak because nothing private is stored.
  • Integrity: The site content lives in a Git repo with full commit history. Any unauthorized change would be visible in the diff. Rollback is one command.
  • Availability: Files served from Cloudflare's edge cache, fronting GitHub Pages. Even if the origin goes down, cached versions stay up. Realistic 99.9%+ availability without paying for it.

Attack surface for a static site is dramatically smaller than for any CMS. No PHP runtime, no SQL, no admin endpoints, no plugin ecosystem. The remaining attack surface is the domain itself (DNS hijacking), the registrar account (account takeover), the GitHub repo (credential compromise), and Cloudflare (account takeover). Four well-defined chokepoints, each with MFA enforced.

DNS and Cloudflare Configuration

The domain points its nameservers at Cloudflare, not at the registrar's DNS. This means every DNS record is managed in one place and Cloudflare can act as the edge for HTTP/HTTPS.

// dns records

The essential records currently in place:

A     @                  185.199.108.153    (GitHub Pages)
A     @                  185.199.109.153    (GitHub Pages)
A     @                  185.199.110.153    (GitHub Pages)
A     @                  185.199.111.153    (GitHub Pages)
CNAME www                dingdongplumbers.co.za
TXT   @                  google-site-verification=...
TXT   @                  v=spf1 include:_spf...
MX    @                  (mail provider)

All four A records point at GitHub Pages' edge IPs for redundancy. The CNAME on www sends visitors to the apex domain (where canonical content lives), and Cloudflare handles the redirect. SPF and TXT records keep email and Search Console verification intact.

Side note on publishing DNS records: Every record above is publicly queryable via any DNS resolver, so publishing them in a portfolio adds nothing an attacker could not learn in seconds with dig or a tool like dnsdumpster. The sensitive items — API tokens, registrar credentials, internal-only subdomains, full SPF/DKIM selector values — stay redacted. Knowing what is already public vs. what genuinely needs to stay private is part of the job.

// edge configuration

  • SSL/TLS mode: Full (strict). Cloudflare validates the GitHub Pages origin certificate, so the entire path from browser to origin is encrypted and verified.
  • Always Use HTTPS: on. Any HTTP request is 301-redirected to HTTPS.
  • Automatic HTTPS Rewrites: on. Catches stray http:// references in the markup.
  • Minimum TLS version: 1.2. No TLS 1.0/1.1 clients allowed in.
  • Bot Fight Mode: on. Free-tier mitigation against the obvious scrapers and brute force tooling.
  • Browser cache TTL: tuned per asset type so HTML refreshes quickly but images and CSS stay cached.

The CI/CD Pipeline

"CI/CD pipeline" sounds heavy for a static site, but the workflow is real and matters in day-to-day work. Every change moves through: 

Local edit  →  git commit  →  git push  →  GitHub Pages build  →  Cloudflare cache  →  live
                                                ~30 sec               purged on deploy

The whole loop from save-file to live is under two minutes. Cloudflare cache purge on deploy is automatic for HTML; CSS and image updates use cache-busting filename hashes when needed.

Git history doubles as the audit log. Every change is signed, timestamped, and reversible. If a deploy ever broke the site I could roll back to the previous commit and republish in seconds. That is incident response 101 for a production system.

SEO and Programmatic Location Pages

Local plumbing is a "where" business. Customers search "plumber in Sandton," not "best plumbing methodology." Ranking for those queries requires dedicated landing pages per service area, each with unique content. Hand-writing thirty pages and keeping them in sync with the rest of the site is a maintenance nightmare, so I built a small generator.

A towns.json data file holds the per-town content: name, suburbs serviced, response time, local context, primary services. A Node.js script reads that file and produces one index.html per town under /areas/<slug>/, plus a regenerated sitemap.xml. Each generated page includes proper LocalBusiness JSON-LD schema with areaServed populated from the data file.

Why this matters for security work: The same pattern (data file plus generator plus signed output) is how IaC tooling works in much larger environments. Doing it on a small static site is the same skill at a smaller scale: version-controlled configuration, deterministic output, no manual drift.

Adding a new service area is now three steps:

  1. Add a row to towns.json.
  2. Run node scripts/generate.js.
  3. Commit and push.

The sitemap regenerates with every run, so Google Search Console always sees the current list of pages.

Form Handling Without a Backend

The contact form on a plumbing site is a real attack surface. I use Formspree to handle submissions, which means:

  • No server-side code lives on my infrastructure. No PHP mail handler to keep patched, no SMTP credentials to rotate.
  • Formspree handles spam filtering, reCAPTCHA, and rate limiting at their edge.
  • Submissions go directly to the business email. No data is stored on the website.

The "less infrastructure equals less attack surface" pattern again. Where I do not need to run something, I do not run it.

Lessons Across Six Years

  • Boring infrastructure wins. Every time I have been tempted to add complexity (CMS, custom backend, fancier framework), the static stack has paid me back with fewer Sunday-evening pages.
  • Documentation pays compound interest. When I touched the DNS records in 2024 I needed notes from 2021 to remember why certain TXT records were there. The notes existed because I wrote them. Future-me thanks past-me regularly.
  • Treat small projects like big ones. The discipline of version control, documented changes, and least-privilege access scales down to a one-page plumbing site as well as it scales up. It is the same muscles, just lighter weight.
  • Account hygiene is the real perimeter. The most likely breach vector is not the site itself but the registrar account, the Cloudflare account, or the GitHub account. MFA on all three. Unique passwords. Hardware key where supported.
  • Things break in ways you did not anticipate. Cloudflare changed their default SSL behavior once and broke origin verification for a few hours. A registrar billing dispute almost cost the domain. A DNS misconfiguration of mine knocked the site offline for forty minutes. Each one teaches.
